# Frozen hybrid controller: cooking conditions, public API context, and a bounded model loop

## Scope

This package preserves an older hybrid harness from our local development line. Its executable Python files, Dockerfile and build exclusions are unchanged from the frozen artifact that produced a local OP1 outcome of 93.8. This is not a claim of a 93.8 suite score, a repeatable advantage, or superiority over the current leader. The purpose of retaining this version is to measure the candidate as a whole rather than infer its strength from one long game.

The runtime ancestor is our promoted 54-test submission, `5dfdcf15-9802-4fbf-a64f-9866323c1412`, at commit `1afa775bbd08645aa6f43dfe6ec76563cad8fa66`. That line inherited e-man07's hybrid controller and the organiser's API client and plain loop. Subsequent local work added bounded wall handling and model-error recovery, office-chair handling, a few deterministic standing orders, and the cooking/manual-section changes described below.

The trusted repository used for packaging is the current `ab1668c0575c85ae1971d528b88bdaeb14b94b53` tree. Its current leader, `65e60732-98d2-4765-a2c6-f84076c3e5fe` by 0xplemonade, is credited as the repository and submission-contract base. Its unique runtime changes are deliberately not mixed into this candidate. In particular, this package has no `overseer/openplay.py`, `overseer/beasts.py` or `plain/digest.py`; it does not contain that leader's predator census, no-fishing rule, hatch-lockdown/admission system, thaw guard, STATUS digest or later goal-specific policies. Those belong to a different, separately tested line.

Internal experiment diaries and generated bytecode are not included. A current public note and dependency declarations are included so that historical hypotheses are not mistaken for measurements of the submitted runtime. These packaging differences do not change the executable policy. The historical local package digest was `sha256:34dad77131cd78a971935fa4593c243770351f129dacfb395cfdb730862b8c84`; adding submission metadata changes the package digest, so it is not presented as the new archive's identity.

## How the harness acts

The entrypoint is `python -m plain`. `dfbench_client` reads the task supplied by the runner and talks to the game API and model gateway. It is a standard-library-only package, built with the existing pinned Python 3.12-slim Dockerfile, and runs as `nobody`.

The plain loop obtains the public observation, runs a deterministic Overseer when the game day changes, and then asks the fixed model for one tool call. It keeps a bounded conversation window. Older observations become short placeholders and older tool results are shortened. Only the first tool call in a reply is executed; additional calls receive a one-tool-per-turn response. Invalid tool-name and order-ID types are checked before local cache/set lookups so that malformed suggestions do not crash the loop.

The Overseer acts only through the public API. It handles management, automation, workshops, digging, farms, supply orders, furniture, offices, mood workshop needs and a basic defence rule. Its actions have keys, retry spacing and attempt limits. Successful builds retire a used site; room roles are recorded after a successful action. Controller-owned daily brew orders are tracked and protected against model cancellation. The earlier order-churn guard also discourages cancelling a freshly added order or immediately re-adding a cancelled one.

This is the older controller, not a complete implementation of the current leader's safety strategy. Its defence logic primarily uses the public threats and military fields. Ordinary predatory wildlife may not appear as hostile in those fields. Fishing and early chopping can expose dwarves, and the package does not have the later no-fishing or predator-lockdown mechanisms. That is a concrete limitation, not an assumed solved problem.

## Changes retained after the published 54-test ancestor

### Wall handling and model errors

The loop uses observed recent model-call latency and a reserve when deciding whether another call can fit near the wall limit. It can leave the remaining simulation to run rather than continue issuing calls into a likely watchdog termination. This is conservative scheduling, not a guarantee against an unexpectedly slow future call.

The line also contains quiet-state recovery after repeated model errors. A recovery advance is clamped to one game day, and the recovery streak is bounded. A successful response resets the relevant streak. This is not a global lifetime recovery-day budget, and it does not make all ordinary advances one day. Normal quiet pacing still has its own limits. Local test coverage exercises the emitted advances and stopping conditions; it does not establish a score gain under every outage pattern. The selected GLM OP1 game had no provider errors, so that game did not test an outage-recovery benefit.

### Office and standing-order changes

The controller retains early office/chair handling so a manager can keep validating orders as population grows. It also retains an autolabor gate, a monthly chair order, and a conditional `PrepareMeal` manager order. These were developed during an earlier production-oriented exploration. The current chair order is amount 5, monthly, with stock and log conditions. The additional meal manager order requests amount 20, daily, with a FISH item condition, and is not added when an observed order already has the PrepareMeal job.

The thresholds in these older opening rules use the controller's `now`, which is loaded from absolute world ticks. They must not be described as guaranteed elapsed task days. An established fort can already be past those thresholds at its first observation. This behaviour is preserved, not silently retimed for this submission.

A later local experiment removed a scripted daily hatch-cover production mill. That removed a production order, not a safety hatch system: this older line did not have the current leader's lockdown implementation. The model remains able to request supported hatch-related actions through the API.

Some retained source comments reflect the early wealth-led hypotheses, including strong wording about production gaps or variance. Those comments predate the outcome-score review. The local data does not establish that a scripted meal order eliminates variance, or that more production wealth alone improves the challenge score. Wealth, a completed order and a scored outcome are different measurements.

### Plant-independent regular cooking condition

The regular standing `cook_meal` order now has only its prepared-meal cap in its `when` list. The former `plants_total >= 10` prerequisite was removed because cooking can use nonplant ingredients. The order still has amount 2, daily repetition, prepared-meal cap 200, the same action key/retry behaviour and standing-order deduplication.

This change does not remove the brew order's plant/barrel requirements, change its drink cap, change seedwatch, or add a second regular cooking order. It can still increase competition for cookable plants or labour. A condition that admits fish and meat is not evidence that every cooked ingredient will be fish or meat, nor that future drink supply is protected in every fort.

### Served manual section 10

The system prompt selects sections 4, 6 and 10 from the manual returned by the game server. Section 10 contains the API's known limitations, including the lack of trade and the caveat that manager_order_types lists DF job classes rather than the work-order screen's menu. The parser itself is unchanged and follows the order of sections in the served manual.

The prompt otherwise remains the older raw-observation/automatic-work design. It does not acquire the later frontier PLAYBOOK or STATUS digest. It also does not contain the separate explicit no-depot wording tried after this candidate was frozen.

## Local evidence and what it does not show

The following were separate frozen candidates, each played once on the same public OP1 task with seed 12345, using GLM 5.3 Flash through a local OpenCode Go transport. They are not repeated measurements of one source and are not full-suite scores.

| Local variant | OP1 outcome O | Important observation |
|---|---:|---|
| Earlier opener with scripted hatch mill | 50.7 | One infection death, stress, no progression |
| Scripted hatch mill removed | 57.9 | No deaths, but food supply component 0.543 |
| Regular cooking plant prerequisite removed | 87.5 | Survival, supply, wellbeing and housing full; progression zero |
| This candidate: served manual section 10 also included | 93.8 | Full lower components; one progression step from the monarch flag |
| Later explicit no-depot variant, not submitted here | 30.0 | No depot guesses, but two deaths and substantial stress |

For the selected 93.8 run, the trusted scorer reported survival 1, supply 1, wellbeing 1 and growth 0.75. Housing was full, fortress rank and exports were zero, and the recorder's king_arrived flag changed from false to true. That flag transition accounts for the extra progression step. It does not establish that the manual text caused the transition or that the higher score will recur. The event aggregate recorded royal succession rather than a separate MONARCH_ARRIVAL event; no stronger causal story is asserted.

The selected game reached day 336 normally, with 72 successful model calls, no provider errors, no unknown usage and no budget or wall cap. Its reference spend was 0.14905515 and its runner wall time was 1038.3 seconds. There were 29 trusted server-rejected actions, including 26 depot/construction manager-job guesses. The manual-section hypothesis therefore failed its intended behavioural target even though the outcome was higher than the preceding observation. The later no-depot variant's zero guesses and low score are another reason not to substitute fewer bad actions for a score gain.

The exact selected runtime has not completed a full local six-task assessment. Local public-pool setup was blocked by missing seed-2002 saves whose standard terrain acceptance failed. No seed was substituted and no terrain rule was weakened to manufacture complete coverage. Related earlier branches had additional local games, including games with a different development model, but those are not reported as GLM validation of this exact source.

## Model, accounting and environment

The submitted harness requests the fixed official model identity `z-ai/glm-5.3-flash` through the gateway supplied in DFBENCH_TASK. Its generation settings remain low reasoning effort, temperature 0 and max_tokens 4000. There is no alternate provider route or credential in the payload.

The local Go adapter used during development was outside the candidate. It translated the official reasoning field to the provider's accepted shape and preserved the benchmark's reference accounting; it is not shipped here. Subscription billing and reference benchmark cost were recorded separately. Local Go acceptance is not proof of identical reasoning semantics, model snapshot, cache behaviour or performance through the official Together route.

Local policy images ran on arm64, while the Dwarf Fortress image was amd64 under an aarch64 Colima VM. That is another reason not to interpret a public local sample as a private native-x86 result. The pinned reference prices, budgets, horizons, hands-off windows, action rules and scorer were not changed for the local games. No private pool information was accessed or used.

## Checks and reproduction

The frozen candidate's full Python suite passed 94 tests, and the staged copy was exercised again without changing the runtime. The focused cooking regression failed on the pre-change source because the emitted order retained the plant condition, then passed after its removal. The manual-section regression failed when section 10 was missing, then passed with that section included. These check payloads and prompt assembly, not game outcomes.

The existing arm64 image built and ran the selected real GLM game. A local cross-build attempt for amd64 encountered a legacy Docker builder platform-selection error before copying the source; no successful local amd64 build is claimed from that attempt. The Dockerfile itself is unchanged from the tested package and uses the same pinned multi-platform Python base.

From the challenge checkout, unit tests can be run with `python3 -B -m unittest discover -s submission/tests`. The standard runner can play the source with `python3 runner/dfbench local run --stack real --harness submission --task scenarios/season0/op1-start-year.json --model z-ai/glm-5.3-flash --seed 12345 --n 1`. Credentials, when needed for a local run, belong in the runner's supported environment configuration and are not part of this archive. A complete local assessment uses the official suite configuration and all task entries, while remaining distinct from the private-pool hosted result.
